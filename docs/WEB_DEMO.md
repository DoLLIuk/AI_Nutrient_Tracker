## Request and data flow

GitHub Pages serves `web/` and the compiled Flutter app. The app runs inside `#flutter_host`; it is not a video or a separate implementation of the mobile interface.

1. Profile, onboarding draft, and saved meal entries remain in browser storage through SharedPreferences. There is no account or cloud diary synchronization.
2. A random browser ID is generated by `lib/demo_visitor.dart` and sent as `X-Demo-Visitor`.
3. Photo analysis and portion confirmation go to the gateway. A Firestore transaction reserves quota before the existing AI API is called. Admitted attempts consume quota even if the upstream call fails.
4. The gateway reads the existing AI key from Secret Manager; the public web bundle has no AI API key. Images pass through the gateway to the AI backend and are not written to its Firestore event log. This is not a claim about retention by the separate AI backend/provider.
5. `WebDemoAnalytics` sends selected app events to `/v0/demo/event`. Only the event name and optional onboarding step are retained from its payload. Delivery is best effort; there is no analytics dashboard in the demo.
6. Feedback goes directly to Formspree form `xoevlpvb`, independently of the AI services. The payload contains a message, optional reply email, and a fixed source label. Email routing is configured in Formspree, not in the repo. A test submission was accepted; inbox delivery remains owner-verified.

## Demo-specific experience

- The basic-profile onboarding step offers clearly labeled sample values: female, 30 years, 165 cm, 65 kg. Other onboarding choices remain interactive.
- Five generated sample food photos are bundled under `assets/demo_food/`; uploads and sample photos both use real AI analysis.
- Manual logging remains available after photo errors or quota exhaustion.
- Desktop has a short three-step guide, the app, and the feedback form. At widths up to 1040 px, feedback uses a persistent button and drawer. At widths up to 640 px, the intro guide is hidden and the page stacks vertically.
- Desktop content starts 24 px below the header. The intro has 36 px top padding, matching the app caption's 21 px height plus 15 px bottom margin. Mobile retains its own 27 px content padding and zero intro top padding.
- Profile/meal persistence and quota identity are browser-local. Clearing site storage removes local demo data and creates a new browser ID; it cannot reset the global quota.

## Current quotas

Counters use the UTC date and start a new allowance at midnight UTC.

| Action | Per browser ID/day | Shared/day |
| --- | ---: | ---: |
| Photo analysis, including clarified requests | 3 | 50 |
| Portion confirmation | 9 | 150 |
| App usage event | 60 | 1,200 |

The constants live in `demo_gateway/main.py`. Changing them requires a gateway deployment. Rejected requests return an error; the quota is enforced on the server, not just by the UI.

Firestore collections:

- `demo_daily`: shared counters by UTC date.
- `demo_daily_visitors`: daily counters by hashed browser ID.
- `demo_events`: admitted action, server timestamp, visitor hash, diagnostic trace ID, and optional app event/step. Rejections and upstream outcomes are available in Cloud Run logs.

No automatic event retention/cleanup policy was added. Browser IDs are pseudonymous, not authenticated identities; web counts should not be treated as exact unique-person metrics.

## Publishing changes

### Site and Flutter client

Push committed changes to `main`. The workflow runs Flutter tests, gateway tests, an HTTPS gateway URL check, and a release web build with base href `/AI_Nutrient_Tracker/`, then deploys `build/web`. A failed build does not replace the last successful site. Uncommitted local changes are not published.

Repository variables:

- `WEB_DEMO_READY=true`: allows the build/deploy job to run.
- `DEMO_API_BASE_URL`: compiled public gateway URL; it is not a secret.

Setting `WEB_DEMO_READY=false` stops future publishing; it does not remove the already published site or disable the gateway.

### Gateway

The Pages workflow tests gateway code but **does not deploy it**. Use the deployment command in [demo_gateway/README.md](../demo_gateway/README.md), with the project and service above. Keep the dedicated service account, allowed origin, and secret references intact.

- Allowed site origin: `https://dolliuk.github.io`.
- Service account: `ai-nutrient-demo-gateway@project-792ca3d9-d395-406e-bfd.iam.gserviceaccount.com`.
- Secret references: `photo-food-client-api-key:1` and `ai-nutrient-demo-hash-salt:1`.
- Scale configuration: minimum 0, maximum 1 instance.
- Permissions: Firestore access plus access to the two secrets.

Secret values must never be committed or added to web Dart defines. A new secret version needs an explicit deployment/reference update; the current references are version-pinned.

## Local preview and checks

```sh
flutter pub get
flutter build web --release --base-href /
python -m http.server 8765 --directory build/web
```

This previews layout and manual flows without AI configuration. Production gateway CORS rejects localhost. To test AI locally, configure a separate development gateway and pass its URL using `--dart-define=DEMO_API_BASE_URL=https://YOUR_DEV_GATEWAY`.

For layout-only changes, inspect desktop and mobile breakpoints; preserve the app and feedback behavior. For gateway changes, run `python -m pytest -q demo_gateway/test_main.py` with dependencies from `demo_gateway/requirements.txt` installed, and verify the deployed endpoint after release.

## Troubleshooting and protection boundaries

- Old appearance: confirm the latest Actions run succeeded, then refresh without cache. Pages/browser caching can delay asset updates.
- HTTP 429: daily browser or shared quota reached; wait for the next UTC day. Manual logging remains usable.
- HTTP 403 locally: production origin restriction is expected. Do not expose the AI key as a workaround.
- HTTP 503: inspect gateway Cloud Run logs, Firestore permissions, and secret/config access.
- Feedback accepted but email missing: check Formspree submissions, recipient verification, and spam folder. The site does not control email delivery.
- CORS and a browser ID are not authentication. No attestation, per-IP quota, or dedicated burst limiter was added. The shared Firestore quota limits admitted upstream calls, but unwanted traffic can still incur Cloud Run and Firestore costs.
- No billing budget/spend cap was configured as part of this demo. Instance limits are not a monetary cap. This protection applies to the web gateway; it does not replace a production mobile authorization/quota design.

Public demo availability does not mean the mobile beta's device testing, store distribution, privacy policy, or crash-monitoring gates are complete.
