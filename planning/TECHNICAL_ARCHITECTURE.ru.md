# Техническая архитектура приложения

Статус: согласованное целевое направление. Документ описывает следующий этап после текущего Flutter MVP; он не означает, что все компоненты должны появиться одновременно.

## Решение

Используем следующую схему:

```text
Flutter
  -> Firebase Authentication
  -> FastAPI backend
  -> PostgreSQL
  -> AI/Vision providers

Scheduled jobs / workers -> proactive AI -> Firebase Cloud Messaging -> Flutter
```

- **Firebase Authentication** подтверждает личность пользователя: Google Sign-In, Sign in with Apple и Firebase ID token.
- **FastAPI** — единственная доверенная граница для логики продукта, проверки токенов, доступа к данным, вызовов AI и отправки уведомлений.
- **PostgreSQL** — source of truth для пользовательских и продуктовых данных.
- **Flutter** отвечает за UX и может иметь локальный кэш, но не становится вторым главным хранилищем.
- **Firebase Cloud Messaging (FCM)** доставляет push-уведомления.

Это предпочтительнее, чем Firestore как основная БД: данные приложения реляционные, им нужны агрегаты, история, транзакции и аналитика. Firebase остаётся там, где он особенно хорош — identity и push-инфраструктура.

## Авторизация и доступ

1. Пользователь проходит Google или Apple sign-in через Firebase Authentication.
2. Flutter получает Firebase ID token и передаёт его в `Authorization: Bearer <token>` для каждого защищённого вызова FastAPI.
3. Backend валидирует token через Firebase Admin SDK и извлекает Firebase UID.
4. Backend создаёт или находит внутреннего пользователя PostgreSQL и использует только его внутренний `users.id` во всех продуктовых запросах.

Не храним собственные пароли приложения. На `users.firebase_uid` нужен уникальный индекс. Email — изменяемый профильный атрибут, а не ключ идентичности; провайдеры могут быть привязаны к одному Firebase account, поэтому `auth_provider` не должен служить единственным источником истины.

Текущая клиентская схема `X-API-Key` для photo API подходит лишь как временная защита MVP. В production пользовательские запросы должны авторизовываться Firebase ID token; секреты AI-провайдеров и Firebase Admin credentials остаются только на сервере.

## Данные PostgreSQL

Базовые сущности:

```text
users
nutrition_goals (исторические версии целей)
meals
meal_items
user_preferences
ai_recommendations
notification_settings
device_tokens
```

Связи:

```text
users -> nutrition_goals
users -> meals -> meal_items
users -> user_preferences
users -> ai_recommendations
users -> notification_settings
users -> device_tokens
```

Практические правила модели:

- Все временные поля храним в UTC (`timestamptz`), а timezone пользователя — отдельно для дневных итогов и уведомлений.
- Калории и макронутриенты храним в `numeric`/целых нормализованных единицах, не в `float`.
- `meal_items` сохраняет снимок названия, порции и рассчитанных нутриентов на момент логирования — справочник продуктов можно менять независимо от истории.
- У целей должны быть `effective_from`/`effective_to` (либо эквивалентная версионность), чтобы старая статистика не пересчитывалась по новой цели.
- Добавляем внешние ключи, индексы как минимум по `(user_id, occurred_at)` для приёмов пищи и уникальность Firebase UID.
- Дневные итоги сначала вычисляются запросом; отдельную таблицу/материализованный итог добавляем только после измеренной потребности и с ясной стратегией пересчёта.
- Операции создания еды должны быть идемпотентными (idempotency key), чтобы повтор сети не создал два приёма пищи.

## Фото и AI

Фото еды не являются частью постоянной модели первой версии:

```text
camera/gallery -> временный файл -> Vision/Multimodal AI -> структурированный результат -> PostgreSQL -> удаление файла
```

В PostgreSQL сохраняем подтверждённые пользователем структурированные данные: продукты, порции, калории и макросы. Для качества и воспроизводимости можно также хранить версию модели, confidence, источник оценки и факт ручной правки — без сохранения самого изображения.

Временный файл должен иметь ограниченный срок жизни и гарантированную очистку при успехе, ошибке и повторной попытке. Если в будущем появятся объяснимые причины хранить фото (например, повторный анализ по явному согласию), это будет отдельное privacy/product-решение, а не неявное изменение текущего правила.

## Proactive AI и уведомления

Этот раздел — условное будущее направление, а не утверждённый следующий этап. Его можно реализовывать только после того, как discovery и ручной concierge-тест подтвердят ценность конкретного proactive-сценария, а продукт отдельно утвердит его в scope.

Фоновый worker по расписанию выбирает только пользователей, которые дали согласие на уведомления и не достигли rate limit, загружает контекст из PostgreSQL и при необходимости вызывает LLM.

Контекст включает текущие итоги дня, действующую цель, недавние приёмы пищи, предпочтения, timezone/время и, только при явном подключении, тренировочный график. Перед отправкой FCM backend применяет детерминированные ограничения: quiet hours, частотный лимит, дедупликацию и возможность выключить конкретные типы подсказок.

Для надёжности scheduler не должен выполнять тяжёлую AI-работу внутри одного HTTP-запроса. Предпочтительный путь: Cloud Scheduler/Cloud Run Jobs (или аналог) запускает задачу, а очередь/worker обрабатывает пользователей порциями. Все рекомендации и решения об отправке логируются в `ai_recommendations` для отладки и предотвращения дублей.

## API и развёртывание

Первый защищённый набор API может включать:

```text
GET/POST/DELETE /meals
GET /nutrition/today
GET /nutrition/history
GET/PUT /profile
GET/PUT /preferences
GET /recommendations
POST /device-tokens
POST /v0/ai/photo-food
POST /v0/ai/photo-food/confirm-portion
```

FastAPI разворачивается в Cloud Run или эквивалентном сервисе. PostgreSQL — managed PostgreSQL с миграциями (например, Alembic), резервными копиями, отдельными staging/production окружениями и секретами в managed secret store. `pgvector` и RAG не входят в MVP: добавляем их только под конкретную retrieval-задачу.

## Порядок внедрения

1. Зафиксировать контракт backend API и схему миграций PostgreSQL.
2. Добавить Firebase Auth в Flutter (`firebase_auth`, Google и Apple провайдеры) и проверку Firebase ID token в FastAPI.
3. Реализовать `users`, профиль, цели и записи приёмов пищи; перенести текущую локальную модель через явный migration/import flow, а не молча удалять данные пользователя.
4. Перевести photo-food endpoints на пользовательскую авторизацию и серверное хранение результатов.
5. Добавить FCM device tokens и базовые настройки уведомлений.
6. Только после подтверждения спроса, отдельного product decision и появления достаточных данных — scheduler/worker и консервативные proactive рекомендации.
7. Оценить offline-потребность. До этого локальный cache необязателен; если он появится, заранее определить sync-конфликты и сервер остаётся source of truth.

## Границы текущего репозитория

Сейчас это Flutter-клиент с `SharedPreferences`, Firebase Analytics и отдельным photo-analysis backend. В нём ещё нет Firebase Auth, FCM, PostgreSQL-модели или backend-кода. Этот документ задаёт совместимый путь развития и не утверждает, что указанные сервисы уже реализованы.
